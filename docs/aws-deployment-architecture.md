# ErrandBoard AWS deployment: architecture, decisions, and CD

Snapshot: 4 November 2026, `ap-southeast-1`, AWS account `614099836367`. This record combines the repository, the current AWS resource configuration, and the completed live run. It describes **what exists**; where a teammate's exact console clicks or original intent cannot be recovered, the reason is identified as an inference. Use [the operational runbook](aws-deployment-runbook.md) for start and stop commands.

## 1. Architecture at this checkpoint

```text
Browser
  -> internet-facing Application Load Balancer (HTTP 80 redirects to HTTPS 443)
  -> frontend Nginx, ECS Fargate, private subnet
  -> ECS Service Connect aliases: user-service:3001, supplier-service:3002,
     order-service:3003, credit-service:3004 (each its own Fargate service)

App tasks -> MongoDB:27017, Redis:6379, RabbitMQ:5672
             via private errandboard.internal DNS and restricted security groups
           -> three ECS EC2 services on one t3.medium host
           -> host bind mounts under /srv/errandboard/{mongodb,redis,rabbitmq}
```

There are **eight ECS services** in cluster `ErrandBoard`: five app services on Fargate and three data/broker services on EC2. Every service had desired/running/pending count `0/0/0` at this snapshot, and EC2 instance `i-0d9f56cf5a7a6b091` was stopped. The app services can be scaled independently through their desired counts. The three data/broker services share one EC2 host and are each single-instance; they are a cost-conscious single point of failure, not independently scalable or highly available.

## 2. How this deployment was assembled, and why

The following is the practical order to recreate this pattern for another microservices app. The resource values above are verified. Rationales marked **inferred** are explanations of the resulting design, not a claim about a teammate's undocumented reasoning.

1. **Inventory code and traffic.** Identify each HTTP service, internal call, database, queue, port, health endpoint, secret, and CPU architecture. Here, the frontend proxies four APIs; the app services use MongoDB, Redis, and RabbitMQ; Order and User call other app services. This determines the number of ECS services, network rules, and startup order.
2. **Choose compute and persistence.** Five app images were already in ECR and their task definitions targeted Fargate. The team chose to keep MongoDB, Redis, and RabbitMQ as ECS containers. One EC2 host with persistent EBS volumes was used for them. **Inferred reason:** it matched the team's existing images and lower-cost, single-instance preference. Tradeoff: the data tier is a single-host failure domain, and EBS volumes cannot simply follow tasks to another AZ. The earlier EFS idea was not implemented.
3. **Create the network.** Starting from the default VPC, two private subnets were added and associated with a route table whose `0.0.0.0/0` route uses a NAT gateway. Two public subnets were used by the ALB. Fargate tasks have `assignPublicIp=DISABLED` in the private subnets. Security groups permit only ALB-to-frontend, app-to-app, and app-to-data traffic. **Inferred reason:** public entry with private app tasks. For a new app, plan subnet/AZ layout and NAT or VPC endpoints before creating services; these are not supplied by the **Create default VPC** button.
4. **Prepare data host and storage.** The EC2 ECS host was registered to the cluster; three data containers use EC2 task definitions with named host bind paths. The EBS volumes were attached separately. The data task definitions map fixed host ports 27017, 6379, and 5672, so the three containers can be reached at the host's private IP. The MongoDB custom image contains the startup and schema initializer. Run the one-time replica-set initialization task before apps that require transactions. For a new deployment, verify the OS mounts and persistence across stop/start; AWS task-definition metadata alone does not prove the host directories are mounted to the intended EBS volumes. See [ECS bind mounts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html).
5. **Create stable internal names and credentials.** The private Route 53 zone maps each data service name to the EC2 host's private IP. The Fargate task definitions use these hostnames and reference Secrets Manager keys by name. The ECS task execution role was granted `secretsmanager:GetSecretValue` on this one secret. The RabbitMQ URL credentials were synchronized with RabbitMQ's default user/password. For another app, create the secret and least-privilege execution role before launching tasks. Do not paste secret values into task definition plaintext environment fields or Git.
6. **Define app tasks and discovery.** Each app has a separate ARM64 Fargate task definition and service, with a named port mapping. The four backends are Service Connect client-server services in namespace `errandboard`; frontend joins as a client. Their aliases retain the same short names used in the Nginx config and cross-service URLs. **Inferred reason:** avoid changing application URLs while allowing ECS to route between independently scheduled Fargate tasks. App images had to be ARM64 because the available ECR images were ARM64. For a new app, keep image architecture and task runtime platform aligned.
7. **Create public routing and TLS.** An internet-facing ALB spans two public subnets, has SG ingress on 80/443, forwards HTTPS to an IP target group for the frontend, and redirects HTTP to HTTPS. A self-signed certificate matching the ALB DNS hostname was imported into ACM for the 443 listener because no domain was available. For a new public app, obtain a domain and a publicly trusted certificate when possible; self-signed trust warnings are expected here.
8. **Start in dependency order.** Start EC2, then MongoDB/Redis/RabbitMQ; wait for them to stabilize. Start the backends; then frontend. The live run on 4 November 2026 returned HTTP 200 for `/` and all four `/api/<service>/health` paths over HTTPS. Frontend Nginx access logs show small API responses of 40–44 bytes, distinct from the 458-byte SPA response, supporting that those requests were proxied. This verifies that deployment run, not a sustained production load or all user journeys. The services were then scaled to zero and EC2 stopped to control compute charges.
9. **Prepare CD.** The repository's CI was extended with a deploy job using GitHub OIDC and a scoped AWS IAM role. This replaced a CodePipeline/CodeConnections design because the account's AWS Organizations service control policy explicitly denied `codeconnections:ListConnections`. The workflow is local only until reviewed and merged to `main`; no automated deployment has run from it yet.

### Console checklist for a new microservices application

Use this order, substituting your own service names, ports, data requirements, and Region. The existing ErrandBoard resource IDs above are examples, not reusable IDs. Where a console wizard offers a default, check it against the stated setting rather than assuming it was created automatically.

1. **ECR → Repositories:** create one private repository per image. Choose tag immutability if releases will use commit tags. Choose a vulnerability-scanning setting deliberately; ErrandBoard's existing repositories have scanning on push disabled. Build for the CPU architecture you will set in ECS task definitions, then push images. A task definition alone does not build or push an image.
2. **VPC → Your VPCs, Subnets, Route tables, NAT gateways:** choose a VPC and at least two public subnets for the ALB. Create private app subnets and explicitly associate them with a route table that has outbound access through NAT or the VPC endpoints needed by your tasks. Verify DNS support/hostnames. A default VPC does not automatically provide the private-subnet/NAT layout used here. Put stateful hosts in private subnets for a new production design where practical.
3. **EC2/EBS and ECS → Cluster infrastructure:** if keeping databases in containers on EC2, create and register ECS capacity, attach persistent volumes, mount them at known host paths, and verify the mount mapping on the host. Then create one EC2-compatible task definition per database/broker with the proper container port, host port, bind mount, CPU/memory, and image. ECS task definitions do not create or mount EBS volumes for the host by themselves. Consider managed data services or a redundant self-managed design for higher availability.
4. **Route 53 → Hosted zones:** create a private hosted zone associated with the app VPC, and add internal records for the database/broker endpoints. In the current design, all three names point to one host IP; in a new design, prefer endpoints that do not depend on a fixed instance IP. **EC2 → Security groups:** open only the specific data ports from the app task security group. Create separate ALB and app groups; permit app port 80 only from the ALB group and internal service ports only from app peers.
5. **Secrets Manager → Secrets:** create the environment's JSON secret with service passwords, JWT key, internal API keys, and broker URL. In **IAM → Roles**, give the ECS task execution role read access only to that secret. In each ECS task definition, use the **Secrets** fields for sensitive values and environment fields for non-secret hostnames/ports. Keep URL-encoded RabbitMQ credentials synchronized with the broker's startup credentials.
6. **ECS → Task definitions:** create one Fargate-compatible definition per app with the correct ARM64 or X86_64 runtime, CPU/memory, named port mappings, ECR image, execution role, CloudWatch Logs, non-secret endpoints, and secret references. Confirm the Docker image and task architecture agree. Define meaningful container health checks if you want ECS to detect failures beyond process start.
7. **ECS → Clusters → your cluster → Services:** create each backend as its own Fargate service in private subnets with public IP disabled and the app security group. Configure **Service Connect** with one namespace and client aliases matching the URLs used in code. Create the frontend as a Service Connect client. The AWS console's service wizard may not enable Service Connect for you by default. Use [AWS's Service Connect configuration guide](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect-concepts.html) to check named ports and client/client-server roles.
8. **EC2 → Target groups and Load balancers, then ACM:** create an IP target group for the frontend container port and an internet-facing ALB in two public subnets. Give the ALB public 80/443 ingress, redirect 80 to 443, and attach a certificate to the 443 listener. Connect the frontend ECS service to the target group. The target group's health path must return a meaningful 200; `/` only checks that Nginx serves the SPA. An imported self-signed certificate works for a controlled environment but is not browser-trusted.
9. **Start and verify:** bring up data capacity and services before dependent apps, then frontend. Confirm ECS tasks and target health, backend health responses, logs, and an actual user flow. Scale to zero and stop the data host when this environment is not in use. Check retained ALB/NAT/EBS costs separately.
10. **Automate releases:** add CI that gates deployment, an OIDC trust limited to the repository/branch, scoped ECR/ECS permissions, commit-tagged images, task revision updates, deployment stabilization checks, health checks, rollback, and a migration/seed plan. Decide whether your team wants direct deployment on every `main` push or an approval stage before enabling the trigger.

## 3. Exact CI/CD behavior and chosen strategy

### CI gate

`.github/workflows/ci.yml` runs on pushes to any branch, pull requests, and manual dispatch. It grants read-only repository contents by default. The five code jobs run in parallel on Node 22 and Node 24, using `npm ci` from each service's lockfile:

| Job | Checks before deploy can run |
| --- | --- |
| User | Source typecheck, test typecheck, unit tests, compile |
| Supplier | Source typecheck, test typecheck, unit tests, compile |
| Order | Source typecheck, test typecheck, unit tests, compile |
| Credit | `npm test`, whose script builds and runs unit tests |
| Frontend | Tests, lint, production build |
| Compose configuration | `docker compose config --quiet` with placeholder values; this validates Compose configuration and starts no containers |

The `deploy` job needs all six jobs. Its condition permits only a **push to `main`**, so PR checks and manual runs do not deploy. This is continuous delivery of code merged to `main`; there is no approval gate within the workflow. GitHub Actions and the ARM64 runner must be permitted in repository/organization settings.

### AWS authentication and image release

The deploy job runs on `ubuntu-24.04-arm`. `aws-actions/configure-aws-credentials@v6.3.0` exchanges a GitHub OIDC token for temporary AWS credentials. The IAM trust policy requires audience `sts.amazonaws.com` and this repository's immutable subject `repo:AY2627S1-CS3219-P4@328997165/ErrandBoard@1369491803:ref:refs/heads/main`. GitHub's repository OIDC settings API reports the prefix with stable organization and repository IDs. It grants ECR push only to the five app repositories, ECS task registration only for their five families, ECS update only for their five services, and `iam:PassRole` only for `ecsTaskExecutionRole`. No long-lived AWS access keys are stored in GitHub. See [GitHub OIDC subject format](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims) and [GitHub OIDC with AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

`scripts/deploy-ecs.sh` confirms the AWS account, logs Docker in to ECR, and for each service in order (`user`, `supplier`, `order`, `credit`, `frontend`):

1. Reuses an existing full-commit-SHA image on a rerun. Otherwise, builds a Linux ARM64 image using that service's Dockerfile and checks its architecture.
2. Pushes the new image to the matching ECR repository with the **full Git commit SHA** as an immutable tag. The five ECR repositories currently enforce immutable tags; scanning on push is currently disabled.
3. Reads the task definition currently attached to that ECS service, changes only the matching container's image URI, and registers a new task definition revision.
4. Updates that ECS service to the new revision and waits for ECS to report it stable. Its desired count is not changed.

The script does **not** build or deploy the MongoDB, Redis, or RabbitMQ images. It does not run database migrations or seed tasks. The ECS stability waiter confirms the service reached ECS steady state, but there are no backend container health checks or end-to-end user-flow checks. It does not roll back a partial five-service release. If it fails after updating some services, the others may remain on the previous revision. These limits should be resolved before relying on unattended production releases.

### ECS deployment strategy

The current ECS services use **rolling** deployments, not blue/green or canary. For the five Fargate app services, `minimumHealthyPercent=100` and `maximumPercent=200`. With desired count 1 while live, ECS can start a replacement task before stopping the old one; temporary extra Fargate capacity and cost are possible. For the three single-instance EC2 data services, minimum is 0 and maximum is 100, so an update can stop the old task before the replacement starts. The CD script does not update those three services. See [AWS rolling deployment settings](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/update-bluegreen-to-rolling.html).

All eight services currently have the ECS deployment circuit breaker and automatic rollback **disabled**. None of the five task definitions defines a container health check. The ALB checks only frontend `GET /` for HTTP 200; it does not check backend APIs. Thus a task can be considered running while a deeper dependency or endpoint is broken. When desired count is zero, updating the task definition stages the next version without creating tasks. The next manual scale-up is when the new version actually runs. This is a cost-saving operational mode, not a live production rollout. See [ECS deployment failure detection](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html).

## 4. Current limitations and what to change for another production deployment

- **Availability:** one EC2 data host, one instance of each data/broker service, one NAT gateway, and one ALB-backed frontend task when live are single points of failure. For a service that must remain available, design redundant data services, multiple running app tasks, and multi-AZ egress before launch.
- **Persistence:** verify the three `/srv/errandboard/` directories are actually backed by the three attached EBS data volumes. No EFS exists. Backups and restore procedures were not verified in this review.
- **Security:** all four attached EBS volumes report `Encrypted=false`; Redis is private but has no task secret for authentication in the current definition; the public certificate is self-signed. These are current-state facts, not defaults to reproduce. Evaluate encrypted volumes, authenticated/TLS data connections, and a trusted certificate for a future production launch.
- **Release safety:** add meaningful backend container health checks, enable ECS deployment circuit breaker and rollback, and plan a coordinated multi-service release or compatibility strategy. The current workflow waits for ECS stability after each service but updates services sequentially without a transaction or automatic recovery.
- **Cost:** stopping ECS tasks and EC2 does not stop ALB, NAT, EBS, Route 53, or retained log charges. Keep or delete those resources based on whether the environment must be quickly restartable.
- **Reproducibility:** the AWS infrastructure was created partly through the console and CLI; it is not yet fully described as infrastructure as code. This document records the current shape but cannot recreate it with one command. For a new app, codify VPC, IAM, ECS, ALB, DNS, storage, and alarms before relying on repeated deployments.
